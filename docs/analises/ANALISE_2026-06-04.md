# Análise — pulse-service

**Data:** 2026-06-04 | **Categoria:** prod | **Tipo:** auditoria holística single-agent | **Baseline:** sem baseline (primeira auditoria documentada)

---

## Resumo executivo

O pulse-service é um produto híbrido funcional (feature flags + A/B testing + product analytics) com arquitetura Go sólida, boa separação de camadas e segurança OWASP em nível razoável para um MVP. Os riscos mais graves são: (1) vendor incompleto — `golang.org/x/crypto` ausente quebra o build da handler layer em CI e localmente; (2) os testes do job de teste no CI têm `continue-on-error: true`, tornando falhas invisíveis no gate de deploy; (3) o endpoint `GET /api/v1/north-star` expõe métricas de produto de todos os 6 projetos IIT sem autenticação; (4) cobertura de testes global é 3.6% (medida real), muito abaixo da meta de 80%, com apenas flag_service, experiment_service e evento cobertos de forma relevante. Comparado a concorrentes (PostHog/LaunchDarkly), o produto já possui diferenciais claros (LLM observability, health score, MAB) mas ressente da ausência de Swagger completo, testes de integração e pipeline RabbitMQ (ADR-005 definido, não implementado).

---

## Cobertura de testes medida

**3.6% global** (medido via `go test ./internal/... -coverprofile`, excluindo packages com build failure: `handler`, `telemetry`, `server`).

Detalhamento por package funcional:
- `service/flag_service`: funções `evaluateFlag` 95.0%, `selectVariant` 93.3% — bem cobertos
- `service/experiment_service`: `AnalyzeExperiment` 92.7%, `chiSquaredPValue` 90.9% — bem cobertos
- `service/event_service`, `service/weekly_insight_service`, `service/monitor_service`, `service/health_score_service`, `service/bayesian_service`, `service/anomaly_service`, `service/churn_*`: **0.0%**
- `repository/`: **0.0%** (testes existem mas requerem DB real; não rodam em -mod=vendor sem postgres)
- `handler/`: **build failure** — `golang.org/x/crypto` ausente no vendor

**Meta 80%: REPROVADO.** Pacotes críticos (auth, billing, retention, health_score, churn) sem qualquer cobertura.

## Arquitetura

**Forças:**
- DDD funcional: separação clara entre `domain/`, `repository/`, `service/`, `handler/`, `agent/`, `pkg/`
- Wiring explícito em `cmd/server/main.go` sem frameworks de DI — fácil de rastrear dependências
- Bounded context bem definido em CONTEXT.md; upstream/downstream claros
- ADR-005 documentando decisão sobre RabbitMQ com trade-offs (Q3 2026)
- 60 migrations numeradas e sequenciais (com gap em 043)

**Gaps:**
- **Migration 043 ausente**: `webhook_handler.go:9` referencia "Migration 043 adiciona webhook_type e success/duration_ms" mas o arquivo não existe — schema pode estar divergente de expectativas do código
- `any` em domain types (`domain/segment.go:35` campo `Value any`) enfraquece contratos; `Segment.Context` como `map[string]any` poderia ser `SegmentContext` tipado
- `InsightsAgent` nomeado como "agente autônomo LLM" mas não chama nenhum LLM — desalinhamento entre nome/docs e implementação
- Sem camada de `usecase/` ou `application/` separada de `service/` — para a complexidade atual, `service` acumula lógica de domínio e orquestração

## Backend e Segurança

**Forças (OWASP):**
- SQL injection: prepared statements em toda a camada repository (`$1`, `$2`, pgx v5) — sem exceção verificada
- `query_explorer_handler.go`: allowlist de operadores (`validOperators`), allowlist de colunas (`allowedGroupCols`), validação de property name char-by-char — bem implementado
- JWT HS256 com verificação de assinatura + expiração em `middleware/auth.go` (implementação própria sem dependência de biblioteca problemática)
- Rate limiting por project_id no Redis (`middleware/ratelimit.go`) com fixed window e headers RFC 6585
- Quota enforcement mensal por account_email (`middleware/quota.go`) — fail-open seguro
- Security headers completos (`X-Frame-Options`, `CSP`, `HSTS`, `X-Content-Type-Options`)
- bcrypt custo 12 para hash de senha (`local_auth_handler.go:213`)
- Comparação de token em tempo constante (`subtle.ConstantTimeCompare`)
- Webhook HMAC-SHA256 assinado em saída
- Logs sem vazamento de password/secret verificado

**Gaps:**
- `GET /api/v1/north-star`: endpoint sem autenticação retorna métricas de negócio (DAU, churn, conversão) de todos os produtos IIT — P1 security
- CORS `*` default: `config.go:48` `AllowedOrigins: getEnv("PULSE_ALLOWED_ORIGINS", "*")` — em prod o PULSE_ALLOWED_ORIGINS precisa estar definido; sem evidência de que está no deployment K8s (deployment.yaml não contém a variável)
- Sem `gosec ./...` no CI — issues G402, G501 potenciais não são detectados automaticamente
- `user_export_handler.go`: exportação LGPD sem validação de que o service token que chama tem ownership do `project_id` — qualquer detentor do service token acessa dados de qualquer usuário de qualquer projeto
- `checkout_webhook_handler.go`: recebe payload sem validação de HMAC do remetente — assume que qualquer chamada com `X-Service-Token` correto é legítima; para webhook inter-service, HMAC no payload seria mais defensivo
- Logs expõem `customer_email` e `contact_email` em contextos de churn alert e email sequence

## Testes

**Forças:**
- Testes de isolamento multi-tenant (`isolation_test.go`) com mocks — bem estruturado
- `flag_service_test.go`, `experiment_service_test.go`: cobertura de caminho feliz e edge cases das funções de avaliação e análise estatística
- `event_handler_test.go`, `csat_handler_test.go`, `cost_handler_test.go`: testes de handler com httptest

**Gaps críticos:**
- **Build failure do package handler**: `golang.org/x/crypto` ausente do vendor impede compilação de `local_auth_handler.go` — todos os testes do package handler ficam inacessíveis
- `weekly_insight_service`: 0% de cobertura; função `Generate` chama LLM e pode falhar silenciosamente
- `churn_alert_service`, `churn_trend_service`, `email_sequence_service`: 0% — serviços que enviam emails sem testes
- `health_score_service`: 0% — cálculo de score crítico para produto sem testes
- `anomaly_service`, `retention_service`, `monitor_service`: 0%
- `repository/`: testes existem mas requerem `DATABASE_URL` real; sem mock layer (interfaces não completas para todos os repos)
- Sem testes de integração (`/tests/integration/` referenciado em `isolation_test.go:8` como "futuro BKL-1105" — ainda não existe)
- Smoke test (`smoke_test.go` na raiz) não integrado ao CI pipeline explicitamente

## DevOps

**Forças:**
- ArgoCD + K3s com manifests GitOps (`deploy/argocd/application.yaml`)
- HPA configurado (min=2, max=4, CPU 70%, memory 80%)
- Liveness + readiness probes em deployment.yaml
- Resource limits definidos (CPU 200m, mem 256Mi)
- Graceful shutdown com `SIGTERM` handler
- Docker multi-stage build
- GHCR como registry com SHA tagging

**Gaps:**
- `continue-on-error: true` no job `test` (ci.yml:17) — falha de teste não bloqueia o deploy; P0
- Vendor incompleto: `golang.org/x/crypto` e `golang.org/x/net/internal/httpsfv` ausentes — `make test` local e CI falham
- Sem `gosec ./...` ou `govulncheck` no pipeline
- Sem `golangci-lint` no CI (existe no Makefile mas não no workflow)
- Deployment base com `replicas: 1` mas HPA `minReplicas: 2` — inconsistência; durante primeiro apply sem HPA ativo, só 1 réplica sobe
- `PULSE_ALLOWED_ORIGINS` não configurada no deployment.yaml — CORS permanece `*` em prod
- `ANTHROPIC_API_KEY` não presente no deployment.yaml nem no secrets manifest — weekly insight silenciosamente desabilitado em prod (generator retorna nil)
- Dependabot configurado (`.github/dependabot.yml`) mas sem política de auto-merge para patch

## Dados

**Forças:**
- PostgreSQL com pgxpool (connection pooling)
- Redis cache de flags com TTL 5min, SetNX atômico anti-thundering-herd
- Retention purge job diário (`retentionpurge/purger.go`) por `data_retention_days` por projeto
- Índices de performance em migration 059 (`performance_indexes.up.sql`)
- LLM observability tracking (`migration 035`, `llm_observability_handler.go`) — P50/P99, error rate por modelo
- North Star metrics reais por produto com sparkline de 8 semanas

**Gaps:**
- `weekly_insight_service.go:143` usa `tracked_at` (coluna inexistente) — `created_at` é o nome correto em migration 004; todas as queries de DAU/churn/produto retornam 0 silenciosamente
- `CopyFrom` em `InsertBatch` não usa prepared statement explícito — pgx CopyFrom é seguro (binary protocol), mas a ausência de prepared statement pode gerar alerta de gosec G201
- Sem particionamento ou `pg_partman` para tabela `events` — a longo prazo, sem RabbitMQ + batch, inserts síncronos num table de crescimento ilimitado degradam
- `api_costs`: custo IA acumulado mas sem alertas de threshold (ex: R$X/dia) — pode resultar em surpresa financeira

## IA

**Forças:**
- `InsightsAgent`: 5 análises heurísticas automáticas (dormant flags, full rollout, spike/drop, negative rate, partial rollout) — valor imediato sem LLM
- `WeeklyInsightService`: integração Claude Haiku para narrativa acionável semanal em PT-BR
- LLM observability tracking nativo — diferencial competitivo claro vs LaunchDarkly/GrowthBook
- AI Configs (`migration 034`, `ai_config_handler.go`) como feature flags para parâmetros de LLM
- `PromptVariant` em feature flags (`migration 039`) — A/B testing de prompts

**Gaps:**
- `insight.go`: sem prompt caching (`cache_control: {"type": "ephemeral"}` no system prompt) — system prompt de 165 chars é estático por definição, elegível para cache; economia ~75% nos tokens de input por chamada
- `insightModel = "claude-haiku-4-5-20251001"` hardcoded — sem config env var; upgrade de modelo requer redeploy
- `InsightsAgent` não gera insights com LLM apesar do nome "agente LLM" — oportunidade de usar Claude para interpretar os padrões heurísticos encontrados e gerar ação concreta por projeto
- USD→BRL `5.70` hardcoded em `weekly_insight_service.go:198,204` — deve ser configurável via env var
- Sem retry com backoff exponencial nas chamadas HTTP à API Anthropic (`insight.go`) — falha de rede descarta o insight da semana silenciosamente

## Compliance/LGPD

**Forças:**
- Endpoint de portabilidade (`GET /api/v1/users/:user_id/export`) — Art. 18 §5° LGPD
- Endpoint de exclusão (`DELETE /api/v1/users/:user_id/data`)
- DPA template em `docs/legal/DPA_PULSE_TEMPLATE.md`
- IP address armazenado (rastreável) com campo `ip_address` — consciência de dado pessoal
- Sem dados sensíveis (categoria II LGPD) no schema — DPA correto neste ponto
- Retention purge configurável por projeto (`data_retention_days`)

**Gaps:**
- DPA template com campos em branco (`CNPJ a definir`, `Av. [endereço completo]`) — não pode ser assinado por clientes; P3 mas bloqueante para contratos comerciais
- `user_export_handler.go`: sem validação de ownership entre caller (service token) e o projeto do usuário exportado — qualquer serviço interno com o token pode exportar dados de qualquer user de qualquer projeto; viola princípio de mínimo acesso
- IP address armazenado sem pseudonimização — Art. 13 LGPD favorece técnicas de anonimização para dados de analytics; IP completo é dado pessoal (ANPD)
- Sem DSAR (Data Subject Access Request) workflow documentado para usuários finais dos produtos IIT — os endpoints existem mas o processo para o usuário solicitar via produto não está definido
- `session_replays` pode capturar dados sensíveis (conteúdo de formulários, campos de password) se o JS SDK não filtrar inputs — sem evidência de sanitização no `sdk/js/src/session-replay.ts`
